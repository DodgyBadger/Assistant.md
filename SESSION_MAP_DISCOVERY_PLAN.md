# Session Map Discovery and Retrieval Plan

Branch: `dev/tool-upgrades`. Status: complete; implementation, validation, and approved documentation update finished. Branch issues: [TOOL_UPGRADES_PLAN.md](TOOL_UPGRADES_PLAN.md). Source: `/home/codeman/docs/AssistantMD/! To Do.md`, reviewed 2026-11-07; conversation decisions take precedence.

## Scope

**Session tool upgrade (required):** Let an agent browse the active or another authorized session's map history without already knowing checkpoint IDs, retrieve a complete historical map, and request selected map fields. Preserve checkpoint identity, chronology, canonical source references, and historical-state indicators in responses. Keep latest-map retrieval available without a checkpoint ID.

## Implementation baseline and affected surfaces

- `core/tools/session_ops.py` exposes `get_session_map`, with an optional explicit checkpoint ID or the latest effective checkpoint. `search_sessions` can supply matching historical checkpoint IDs, but there is no dedicated map-history browsing operation or field selection.
- `core/memory/session_discovery.py`, `core/chat/chat_store.py`, and `core/memory/session_map/` own authorized map loading, checkpoint enumeration, validation, and provenance. Existing checkpoint storage should be sufficient; confirm fork lineage and effective-history semantics before designing pagination.

## Contract and constraints

- Add `list_session_maps` to `session_ops`, defaulting to the active session and allowing an explicit authorized session. Return a bounded history index with checkpoint IDs, creation timestamps, concise trajectory excerpts, and entry counts by kind. Keep existing topic-based discovery through `search_sessions`.
- Extend `get_session_map` with `fields` selecting whole content sections (`trajectory`, `entries`, or both), plus optional `entry_kinds` filtering entries by their existing typed kinds. Omitting both returns the complete map. Retain latest-effective-map retrieval when no checkpoint ID is supplied. Arbitrary nested-field projection, entry-ID selection, and a separate trajectory toggle are out of scope.
- Use the same `get_session_map` operation for single and batch retrieval; do not add a separate plural retrieval operation. Accept the existing `checkpoint_id` or a bounded `checkpoint_ids` list, mutually exclusively. With neither supplied, retrieve the latest effective map; with a single ID, retrieve that checkpoint; with a list, retrieve the selected checkpoints in chronological revision order. Apply the same selectors throughout and continue accepting existing single-map inputs. Reject requests supplying both ID parameters.
- Every successful `get_session_map` response uses a `session_maps` list, including latest-map and single-checkpoint retrieval with one result. Do not vary the result container based on input cardinality. Include explicit `order: "oldest_first"`. This deliberately changes the existing single-map response shape; update all affected consumers and scenario expectations.
- Explicit checkpoint retrieval is all-or-nothing: if any requested checkpoint cannot be retrieved, fail the entire request without returning a partial list. Do not disclose whether an unavailable checkpoint belongs to an inaccessible session. Preserve clear distinction between request failure and a session with no map when retrieving the latest map without explicit checkpoint IDs.
- Empty results are normal outcomes: discovery or implicit latest-map retrieval for an authorized session with no map returns `session_maps: []` with an explanation, rather than an operational failure. A valid entry-kind filter with no matches returns the selected map with `entries: []` and its verification metadata; retain trajectory if selected. Explicit checkpoint requests remain all-or-nothing when a requested checkpoint is unavailable.
- Return complete selected semantic units: every included entry retains its ID, kind, state, basis, text, and canonical `sources`; an included trajectory retains its text and `sources`. Entry filtering preserves stored entry order. Session/checkpoint identity, schema version, revision, ordering, and verification metadata are always returned independently of section selection. The accepted goal is lean output without discarding information needed to distinguish proposals, commitments, superseded state, and canonical evidence. This contract supersedes arbitrary field projection and the earlier entry-ID selector proposal.
- Bound explicit retrieval by selected content using configurable limits: default maximum 20 maps per trajectory-only call and 5 when entries are included, including when `entry_kinds` narrows those entries. Omitted `fields` selects both sections and therefore uses the entries-included limit. These defaults account for the existing 4,000-character trajectory and 16,000-character whole-map authored-text bounds; metadata and references add overhead. Return complete selected content without silent truncation. Reject over-limit requests rather than silently dropping maps. Successive calls remain available, but broad trajectory retrieval should avoid unnecessary call overhead.
- Discovery pagination uses a configurable default page size of 20 and configurable maximum page size of 100. Use the existing installation settings/configuration mechanism rather than hardcoded policy limits; inspect its validation and persistence contract before choosing exact setting names and integration. These defaults and retrieval maxima are adjustable configuration, not fixed protocol constants. Adding UI controls is not required by this decision. Treat new configuration as persisted installation state, including defaulting and validation for existing installations; tool-visible limits must match effective configuration.
- Reject unknown `fields` values, unknown `entry_kinds`, and explicitly empty selector lists. Omitting selectors retains the default full-map behavior. Validation errors must identify the invalid parameter/value, list accepted values, and explain the correction, including omitting a selector to use defaults. Keep these recoverable tool-input errors distinct from operational failures; do not expose inaccessible checkpoint or session details through errors.
- Reject `entry_kinds` when explicit `fields` excludes `entries`. Explain that the caller must include `entries` in `fields` or omit `entry_kinds`; never silently ignore the filter. When `fields` is omitted, it includes both sections, so `entry_kinds` is valid and filters entries without affecting trajectory.
- Every response containing multiple maps, including discovery indexes and any batch retrieval, returns maps in chronological revision order, oldest first. Do not return request order, relevance order, or timestamp-only order. This fixed ordering supersedes the earlier proposed newest-first listing default and optional ordering parameter.
- Assign each map a stable session-local revision number derived from checkpoint insertion order, not page position or checkpoint-ID sorting. Include revision number, creation timestamp, current-effective-map indicator, observed-through canonical message index, and compacted-through canonical message index on every listed or retrieved map. Expose the response ordering explicitly.
- Cursor pagination preserves chronological ordering across pages without duplicates or omissions when new checkpoints are appended. Use a traversal snapshot boundary and expose whether more pages remain; settle exact cursor fields during implementation. New checkpoints beyond the snapshot belong to a fresh traversal.
- The first discovery page fixes the traversal snapshot boundary. Continuations use an opaque `next_cursor` carrying the snapshot and position; callers do not manage revision offsets. Newly appended maps are excluded from that traversal and appear on a fresh traversal. Validate cursor/session scope and reauthorize on every continuation. Cursor encoding is an implementation detail, not an additional user-facing decision.
- Map revision chronology describes how interpretations evolved; canonical source indexes describe when the underlying events occurred. Maps are complete interpretations at their revision, not incremental event logs. An older entry repeated in a later map must not be treated as a newly occurring event. Entry IDs are continuity hints, not guaranteed identity across revisions.
- Whole-session trajectory summaries must also inspect the canonical suffix after the latest map's observation boundary. Preserve existing authorization and fork isolation; child-session history uses eligible child-owned checkpoints and must not expose later parent knowledge.
