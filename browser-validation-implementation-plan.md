# Browser validation implementation plan

Status: implementation complete and verified: all 79 deterministic browser cases pass, with cleanup and evidence exports independently audited. AssistantMD owns the Playwright integration and real application lifecycle. The deterministic core default is unchanged, and the full core suite remains stopped.

## Ownership

Keep scenario-harness browser-agnostic. It owns scenario identity, worker execution/deadlines, semantic observations and evidence reporting. Playwright and its pytest integration own browser automation, contexts, page fixtures and browser diagnostics. AssistantMD owns application startup on a real loopback HTTP listener, isolated data/system roots, approved browser fixtures, process/network admission, viewport/browser policy, cleanup and user journeys. Individual scenarios consume shared fixtures and describe actions/outcomes rather than launching or managing browsers themselves.

Use the maintained Playwright pytest integration rather than introducing another generic browser lifecycle. The official async integration requires session-scoped loop configuration; the current app scenarios use function-scoped async fixtures. Resolve that deliberately in the browser-only profile, preserving app/runtime/HTTP-loop ownership and leaving existing core configuration unchanged. A small app-owned async adapter remains an option if the official fixture scopes are incompatible; do not maintain two competing lifecycle owners.

## Behavioral contract

Serve the actual FastAPI application and shipped static assets through a real ephemeral loopback port. The current in-memory ASGI client cannot be navigated by Chromium. Preserve the app fixture's single-owner runtime startup/shutdown; adding a listener must not bootstrap a second runtime or duplicate lifespan ownership. Use the real backend, persistence and application services. External providers or external network responses may be simulated with an inline explanation of boundary, reason and limits. Do not substitute AssistantMD API responses, frontend controllers, DOM state or expected application events.

Scenarios should read as a user journey: open a page, act through meaningful visible controls, assert the visible outcome, then verify persistence where it matters. Prefer accessible roles/labels and stable test IDs where needed; use Playwright's retrying assertions instead of fixed sleeps. API/storage actions may seed initial state, but behavior under test must be triggered through the UI. Screenshots are diagnostic artifacts, not the default correctness oracle.

## Evidence and isolation

Retain screenshots, Playwright traces, browser console errors, page errors and relevant request failures alongside app outputs/observations under each scenario's artifact directory. Use existing run-owned artifact paths first; an artifact index can link browser files without a new plugin dependency. Preserve failure evidence before closing page/context, including setup and teardown failures; a worker killed before export may have incomplete browser artifacts. Do not claim that a partially written trace proves application cleanup.

Start with Chromium and one worker. Give each scenario a fresh browser context; reusing a browser per worker is acceptable only after context/process cleanup is proved with a subsequent healthy journey. Explicitly admit the installed Playwright driver/browser processes in the browser profile and verify actual descendant ownership/cleanup; the current core subprocess allowlist intentionally rejects undeclared browser launches. Browser-native networking is not contained by Python socket audit hooks. Restrict browser requests to the local app and declared external fixtures at the appropriate browser/network boundary, with the known lack of OS containment stated honestly.

## Implementation sequence

1. Inventory the 27 deferred files under `validation/legacy/browser`, separating actual user journeys from JavaScript VM/module-shape/source-text checks. Map meaningful behaviors to replacement journeys; retain originals until replacement evidence or reviewed retirement exists.
2. Introduce an explicitly admitted `validation/scenarios/browser` profile and shared browser/application fixtures. Keep default collection on deterministic core; select browser coverage explicitly with its own loop, subprocess and artifact configuration. Browser-capable tests remain deterministic when external dependencies are controlled.
3. Pilot two real full-stack journeys: settings save/reset with durable reload, and content-import modal submission/progress/result with a local document. Retain a controlled failing probe to verify screenshot/trace/app evidence and a succeeding next case to verify isolation. Compile required CSS through `npm run build:css` during setup, not inside each scenario.
4. Resolve Gmail save-before-authorization and missing-compose-warning browser gaps using real app configuration and controlled external OAuth/provider inputs. No live Gmail credentials should be required for these UI contracts.
5. Review pilot evidence and fixture complexity before migrating remaining journeys. Convert behavior assertions rather than preserving obsolete controller interfaces or fake DOM harnesses. Keep readable scenario code separate from setup/artifact mechanics.
6. Treat the app's Playwright-backed browsing tool resource/concurrency contracts as a separate backend concern. UI journeys do not prove BrowserTool memory admission, call budgets or concurrency guarantees. Review that gap independently after the UI pilot.
7. Add an explicit browser CI invocation with installed Chromium and retained run artifacts after the pilot passes. Keep the full core suite and broader browser run under the user's chosen execution cadence.
8. Review whether any repeated cross-application evidence plumbing belongs in scenario-harness. If needed, add a generic attachment API or optional Playwright adapter; do not make Playwright a required harness dependency or wrap page/locator APIs.

## Pilot implementation and evidence — 2026-10-29

Implemented an explicit browser profile at `validation/scenarios/browser/pytest.ini` using the official `pytest-playwright-asyncio` plugin. Browser fixtures and app/runtime HTTP ingress share a session loop; core retains its function-scoped loops and 400-case default collection. Browser scenarios require the browser configuration and reject mixed profiles/unregistered sources. The Playwright plugin is disabled in core and infrastructure configurations so its autouse cleanup fixtures cannot affect unrelated test runs. Its optional output directory is redirected inside the selected run root.

The existing app fixture still owns runtime bootstrap and teardown. A bounded Uvicorn listener exposes that same production FastAPI app/assets on an ephemeral loopback port with lifespan startup disabled. The official Playwright fixtures own browser/context creation; app helpers handle diagnostics and explicit context closure. Driver launch is declared through the installed Playwright driver boundary; ambient SDK credentials are removed before creating the native driver/browser and restored after the browser session. Browser requests admit only the app origin, service workers are blocked and undeclared WebSockets are closed. These native browser request controls are not an OS sandbox. No in-app service or app HTTP response is mocked in either pilot.

`validation/runs/browser_pilot_final_20261029/report.json` proves two passing browser journeys: settings save/reload/restore-default and local PDF import with visible completion and actual durable output/job state. `validation/runs/browser_evidence_probe_20261029/report.json` intentionally exits 1 with one failed wrong-expectation probe and a passing following case. It proves screenshot/trace retention, clean next-context cookies/state, denial before an undeclared local HTTP origin receives requests, and a usable subsequent real app. This opt-in source lives under `browser/experiments` and is excluded from default browser directory collection. The failure is an explicitly wrong oracle, not a product defect.

The evidence index is `validation/runs/browser_pilot_review_20261029/evidence-index.json`. All four cases, including the intentional failure, retain valid screenshot PNGs and trace ZIPs, real app observations/API outputs, console/page/request diagnostics, confirmed context closure, closed HTTP listeners and completed app shutdown. Independent PID/start-time checks confirm that the seven recorded native descendants from each case have exited after its pytest invocation. This establishes ordinary/failing-test cleanup; it does not extend the framework's guarantee to detached descendants after forced worker death.

Environment and fixture failures are retained separately. The first attempt lacked Chromium shared libraries; the next lacked a valid font configuration and renderer pages crashed. The existing user-owned runtime cache under `/tmp/assistantmd-browser-deps` supplies the libraries and fonts for local verification via `LD_LIBRARY_PATH` and `FONTCONFIG_FILE`; no root installation or product fallback was introduced. CI uses the standard `playwright install --with-deps chromium` preparation. A strict exact label locator was corrected to match the real accessible PDF-strategy label; document/output assertions were preserved. Diagnostic export now attempts tracing even when screenshot capture fails.

Added an explicit browser CI step after core validation, with Node/npm CSS build, the existing Chromium installation and shared failure-artifact retention. CI wiring has not been executed remotely. Local checks run only the browser pilots, opt-in evidence probe, policy checks, collection and two directly relevant core compatibility scenarios; the full core suite remains stopped. The 27 legacy browser test files and ancillary diagnostic remain unchanged; `validation/registry/browser-migration.json` inventories every retained source and the pilot's limited mapping. Broad migration and Gmail-specific journeys follow pilot review. The app browsing-tool resource-policy gap remains separate.

Documentation review remains pending: identify the protected testing/project-structure guidance and propose current-contract text for explicit approval before editing it. No protected documentation was changed. No generic harness runtime or dependency change was needed for browser support.
