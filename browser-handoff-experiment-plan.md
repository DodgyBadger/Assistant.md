# Browser Handoff Experiment

Status: initial probes complete on `experiment/browser-handoff`, 2026-11-06. No production browser contract, application settings, or persistent runtime data changes are part of this initial experiment.

## Question and scope

Can an isolated Chromium session accept a human sign-in, return control to an agent without supplying the password to that agent, and retrieve useful authenticated content? Does headful Chromium improve access to the Amazon and DigiKey pages investigated previously?

The initial work is a standalone, opt-in experimental harness. It must not import or initialize AssistantMD runtime state. Temporary browser contexts and local synthetic login fixtures provide controlled observations. Public-site probes use fresh contexts, bounded sequential requests, no real credentials, and no purchases or account changes. This is feasibility evidence, not application acceptance or a production security boundary. The intended product direction is an interactive browser with navigation, form filling, selection, and submission; the current GET/HEAD restriction is a comparison baseline, not a requirement for that future capability.

## Executable checks

- A real local HTTP login fixture refuses unauthenticated access; a synthetic human-role actor submits credentials through Chromium; an agent-role interface can subsequently read the protected page in the same context, fill a project form, select a category, and submit it through POST. The password never becomes an agent result, report field, trace, screenshot, cookie export, or stored profile. Both actors live in the same trusted harness; this is not a separate-process credential boundary.
- An agent operation is rejected while human control is held. This checks cooperative control ownership in the prototype, not isolation from arbitrary Python or shell access.
- A separate context cannot read protected content, logout revokes access, and closing the context discards browser state. Session cookies remain sensitive capabilities even though the password is not handed to the agent.
- Local diagnostics characterize the user agent and `navigator.webdriver` across current-style headless Playwright, stock headful Playwright, and headful Chromium launched separately and connected through CDP. Keep the launch/transport difference explicit; this is not a pure headless-only comparison.
- Amazon Canada and DigiKey Canada probes record status, bounded content-readiness indicators, challenge indicators, and request-method counts. Compare a production-shaped method/resource restriction with an unrestricted request policy. Do not equate HTTP 200 or a finished navigation with successful catalog retrieval. Do not retain raw headers, cookies, response bodies, challenge URLs, or request payloads.

These are characterization checks against real Chromium and a controlled external-site fixture. No new product behavior is promised, so product red/green scenarios are deferred until a production slice is selected. The existing deterministic browser-call-budget scenario supplies a focused application regression baseline.

## Running the probes

On a browser-capable host, run `uv run python -m experiments.browser_handoff.probe --output validation/runs/browser-handoff/local.json` for synthetic checks in all three modes. Headful modes require a desktop `DISPLAY` or an independently started Xvfb. Use `--mode headless` when only a headless runtime is available. Add `--site control amazon amazon_search digikey --settle 8 --output validation/runs/browser-handoff/retailers.json` to explicitly opt into public-site traffic. Each site/policy pair gets a fresh context. No live login, CAPTCHA solving, purchase, or product-site form submission is attempted.

The current container required Debian browser libraries, fonts, and Xvfb extracted under `/tmp/assistantmd-browser-deps/root`; packages were downloaded and extracted without installation. `LD_LIBRARY_PATH` includes that root's `usr/lib/aarch64-linux-gnu` and `lib/aarch64-linux-gnu`; `FONTCONFIG_FILE=/tmp/assistantmd-browser-deps/fonts.conf` points to its fonts; the virtual display is `:91`. These environment-specific paths are not application configuration or committed dependencies. Chromium's sandbox is unavailable in this container; the experiment records sandbox-disabled execution, including Playwright's default launch configuration. This is not a production deployment recommendation.

## Initial evidence and limits

- Chromium version: `145.0.7632.0`. The synthetic user-role sign-in, paused agent operations, authenticated agent read, form filling/selection/POST submission, cross-context isolation, logout, and context closure all passed in headless, headful, and separately launched headful/CDP modes. Evidence: `validation/runs/browser-handoff/local.json`.
- Ordinary headless and headful Playwright both reported `navigator.webdriver=true`. Separately launched headful Chromium, with `AutomationControlled` disabled, reported `false`. Headful mode removed `HeadlessChrome` from the user agent. These observations alone do not prove undetectability.
- The CDP experiment still attaches through Playwright, which can enable detectable protocol features. It does not reproduce AgenticOS's minimal adapter, JavaScript patches, proxy routing, local WebView, or human takeover interface.
- Early setup failures were environmental: missing browser libraries, Xvfb keyboard helper paths, absent font configuration causing renderer crashes, and an unavailable Chromium sandbox. A local dropdown locator initially failed because its wrapping label included the option text; an explicit HTML label corrected the fixture. These were not application defects or meaningful product red evidence.
- The first public matrix incorrectly required an `h1` on example.com. The live page has its expected title/body but no heading. The original result is retained; the control criterion now checks expected body content. Generic `continue shopping` text also occurs in real Amazon content and is not a reliable challenge verdict. Subsequent probes distinguish phrase matches from an actual CAPTCHA form; catalog selectors remain the success evidence.
- The corrected public control passed in all modes under both policies. Evidence: `validation/runs/browser-handoff/control-corrected.json`.
- In the first retailer matrix, Amazon Canada's product-title selector and search-result selectors were visible in every mode under both policies. The earlier Amazon failure did not reproduce on this host/network/date. DigiKey started with HTTP 403 and never met the initial catalog-content criterion. One restricted headful/CDP run later produced a navigation response of 200 with different page content, so status alone could not classify that run as successful catalog access. Evidence: `validation/runs/browser-handoff/retailers.json`.
- The focused DigiKey follow-up identified a second mistaken probe expectation: the actual catalog heading is `Product Index`, not `Products`. Separately launched headful/CDP Chromium reached the page titled `Electronic Components and Parts Search | DigiKey`, heading `Product Index`, and 627 catalog links under both request policies after a 15-second settle. The original false `content_ready` fields are preserved in `validation/runs/browser-handoff/digikey-followup.json`; the corrected criterion now checks `Product Index`. The restricted run initially returned 403 before navigating to 200, reinforcing the need for content checks after verification. These are unauthenticated catalog-index results, not proof of product-detail access or successful human login on DigiKey. A fresh corrected comparison runs headful/CDP before headless to check whether later success is specific to that configuration or also appears in the baseline.
- That fresh corrected comparison encountered DigiKey's `Just a moment...` page, HTTP 403, and zero catalog links in both modes after 15 seconds. Evidence: `validation/runs/browser-handoff/digikey-corrected.json`. Access is intermittent; the experiment has not established reliable challenge clearance or isolated a causal advantage from headful mode, launch flags, timing, or network reputation. Phrase diagnostics now inspect the title as well as body text because the challenged page's body did not repeat its title. No further live retries were used to seek a green result.
- The existing application browser-call-budget scenario passed with `-n 1`; protected mode rejected the initial `-n 0` invocation before execution. Evidence: `validation/runs/pytest_20261106_190454_ee3bcc8542/report.md`. Repository-wide Ruff/Black, production MyPy, and experiment MyPy checks passed during this investigation.

The next useful experimental slice is a real user takeover interface with control ownership, sign-in, handback, and interactive agent operations. The current harness establishes browser/session mechanics with simulated human input; it does not provide that interface or enforce isolation against an agent with unrestricted code access. Product implementation should remain distinct from this probe and preserve the agreed move toward form filling and submission.

## Steps and evidence

1. Create the experimental branch and inspect the existing browser, validation rules, AgenticOS implementation, and external retailer investigation.
2. Establish an isolated browser runtime and build a repeatable command-line harness under `experiments/browser_handoff/`. Keep reports under ignored `validation/runs/` and dependencies outside tracked application paths.
3. Run the synthetic login/control/isolation checks and browser diagnostics before making public requests. Record failures honestly, including environmental setup failures separately from behavioral results.
4. Run a bounded retailer comparison, retaining sanitized JSON evidence and recording browser version, modes, policy differences, time, and coverage limits. The browser public-network guard remains active for live-site probes; the local fixture uses a separate loopback-only context.
5. Review results with the user before choosing an application implementation. A later slice would need real application scenarios, meaningful red/green evidence, and decisions on takeover UI, execution authority, session lifetime, and authenticated browser access. Automated synthetic human input does not validate actual human takeover UX.
6. Documentation review: no product documentation updates are needed for the standalone experiment. If implementation proceeds, identify relevant documentation, present the exact proposed text or diff, obtain explicit user approval, and apply only approved updates.
