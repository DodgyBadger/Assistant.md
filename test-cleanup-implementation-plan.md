The root authentication files contain these checks; `test_authentication_application.py:62`, `:121`, and `test_authentication_middleware.py:136` provide concrete examples. 2. The root service test at line 277 verifies the API-service boundary and preservation of state on that conflict. ## Harness direction: requirements and framework assessment

### User-confirmed purpose

The harness exists to reduce test maintenance by exercising the real system and checking observable results. Internal interface or strategy changes should not require test changes when the behavioral contract is preserved. Avoid mocking AssistantMD's implementation. Merely moving a pytest function into BaseScenario or adding all root tests to CI does not recover that design. Runner replacement is now an option to assess, not an assumed requirement or an assumed exclusion.

Stable assertions should describe user-visible content, filesystem results, persisted domain state, access outcomes, and meaningful activity evidence. They should not freeze private call graphs, helper signatures, DOM/CSS layout, incidental database representation, or editorial prompt wording. Some protocols, migrations, and persisted schemas are themselves public contracts and justify precise checks. The relevant distinction is contractual versus incidental detail, not a blanket prohibition on APIs or database assertions.

### Required evaluation criteria

1. Real-system operations: exercise actual application code through supported user/API/CLI actions, with real files and stores. Browser scenarios must load the actual application and backend rather than replace fetch with authored replies.
2. Refactor resilience: author scenarios around outcomes and stable domain operations; retain explicit semantic predicates where exact snapshots would overfit incidental representation.
3. Isolation and lifetime: allocate safe runtime roots before application imports; own startup, shutdown, environment changes, clocks, child tasks/processes, ports, and browser resources for success, failure, constructor errors, cancellation, and timeout.
4. Determinism: agree on an explicit external-service policy for LLM/network dependencies. A controlled external transport does not justify replacing application services or asserting on fake internal method calls. Identify controlled dependencies in the scenario record. Keep live-service exercises opt-in. No new exceptions to the user's no-mocking intent have been approved.
5. Evidence: retain actual files, selected structured state, safe activity records, failure traces, and browser evidence with clear expected-versus-observed differences. Normalize only declared unstable fields; never normalize away the invariant under test.
6. Complete execution: one standard entry point for local use and CI; errors during discovery must fail the run, unclassified permanent tests must be rejected, and selected required scenarios must be accounted for in the report.
7. Maintenance cost: assess authoring complexity, adaptation code, dependency/platform requirements, review burden, and migration cost against the existing 139 scenarios. Faster execution or richer reports alone do not justify a rewrite.

### Current harness improvements supported by source inspection

- Discovery fails open: `validation/core/runner.py:83` catches module import failures, logs a warning, and continues; a folder run can omit a broken scenario while executing the rest. Modules with no matching scenario class also disappear from the discovered list. Reject these conditions and report the missing scenario explicitly.
- Lifecycle ownership is incomplete: `runner.py:128` runs the scenario coroutine through `asyncio.run`, then calls synchronous reporting teardown. `base_scenario.py:689` saves interactions but does not stop runtime services. Many scenario authors correctly use finally blocks, but the harness should guarantee cleanup even when an author forgets or startup fails. Preserve primary and cleanup failures separately.
- Interruptions need explicit outcomes: runner error handling catches Exception, not a complete cancellation/interrupt lifecycle. A stopped run should retain completed results, interrupted scenario identity, evidence, and cleanup status; it must never be summarized as a pass.
- Shared process state makes isolation fragile: `system_controller.py:64` changes bootstrap roots, line 71 changes the secret-key environment, and date controls replace application module state. `stop_system` restores some state only after startup succeeds. Assess per-scenario worker processes or a reliably owned isolation context; do not enable parallelism until isolation is proved.
- Bootstrap defaults need a safety review: `validation/core/paths.py:28` and `:36` default to repository data/system roots, and the CLI primes these before importing scenarios. Scenarios normally switch to run-local roots, but collection/import should also be safe without relying on scenario discipline. Treat this as an exposure to investigate, not proof of observed runtime-data damage.
- Browser support and authentication policies need first-class harness paths. Currently the shared API app disables authentication and browser workflow tests sit outside the standard profile. Add explicit configurable app policies and owned browser/server fixtures instead of bypassing the backend or copying private setup into each test.
- The existing domain operations, event capture, evidence directories, structured run results, and focused rerun reporting are assets to retain. Replacing these with a new DSL is not automatically an improvement.

### Governance requirements for review

- Every retained permanent test must have an explicit classification and run through the standard validation entry point. Infrastructure and reusable fixtures are explicitly recognized; unknown Python/JavaScript tests cannot silently escape collection. CI verifies this accounting.
- Each scenario states the observable contract it protects, its entry action, expected output/invariant, and profile. Coverage is traced to contracts rather than production filenames or a minimum test count.
- Default policy is no replacement of AssistantMD's own functions/services to manufacture success. External dependencies, controlled fixtures, and genuine failure injection require a declared boundary and rationale. Any exception policy needs user agreement before implementation.
- Primary correctness assertions use real outcomes. Source-text searches, internal call-count assertions, private helper contracts, and snapshots of editorial prompt text are flagged for review. Automated checks can detect some patterns but cannot establish semantic adequacy alone.
- Required scenarios fail visibly on collection, startup, execution, timeout, cleanup, or evidence/report failure. Skips and experimental classification cannot be used to hide a required contract failure.
- CI and agent guidance refer to one command/profile policy. Local shortcuts must not be represented as complete pre-merge verification. Broad test deletion is blocked until the retained or migrated outcome assertions are identified.
- Output-baseline updates are reviewed as changes to the expected behavior. Normalizers and comparators have explicit contracts; passing by accepting a new baseline is not automatic.

### Bounded next assessment

The current direction is to improve the existing domain scenario approach and its lifecycle/discovery guarantees. The user has questioned whether TextTest warrants migration, and it is no longer a proposed next-step migration target. A mature execution component can be reconsidered only if a concrete local need and measured maintenance saving justify it. Preserve flexible Python scenarios and avoid bulk conversion of the 139 scenarios or adoption of another authoring language.

Use three representative contracts to assess the candidates: real owner-login/CSRF outcomes against the actual application; backup-fenced settings reset using real files/SQLite and controlled concurrent actions; and quote selection appended to a draft through the actual browser/application without replacing fetch. Include a deliberately failing expected outcome so evidence retention and failure reporting can be assessed. The browser example can avoid sending a model request, keeping framework evaluation independent of LLM simulation policy.

Compare authoring length, implementation coupling, driver code that must be maintained, reliable cleanup, isolation, missing-scenario detection, useful diagnostics, and change required by a harmless internal refactor. Prototype only the shortlisted approach after discussing this assessment; no packages, prototypes, runner changes, or scenario runs were introduced during this research. Keep evaluation experiments temporary until there is a decision, and do not create another permanent test runner outside the standard path.

## Agent-driven development and automated test quality: research assessment

### Scope and evidence quality

Reviewed current first-party guidance, engineering case studies, and research available during this October 2026 investigation. Distinguish automating test execution, generating test candidates, and evaluating whether those candidates protect the intended behavior. Also distinguish a coding-agent execution harness from AssistantMD's application-validation harness: the former supervises development actions, while the latter must prove product outcomes. Neither role is satisfied solely by an agent reporting that tests pass.

There is no evidence in this review for a universal agent-development testing standard or a reliable industry-wide percentage of poor AI-generated tests. The evidence establishes specific successful filtering practices and concrete failure mechanisms. Vendor case studies describe particular projects and should not be treated as independent proof of general superiority. Older deployment measurements are historical evidence, not measurements of current frontier models. Research on generated unit-test assertions does not directly measure the effectiveness of AssistantMD's end-to-end scenarios.

### Practices worth adopting for AssistantMD

1. Keep the expected outcome independent of the implementation. Define or review the acceptance contract before generating tests; a bug reproducer must fail for the intended behavioral reason before the fix. New-feature tests that only fail because a private method is absent do not establish the requested system behavior.
2. Automate the feedback loop using the real application: safe isolated roots, supported entry actions, durable outputs, meaningful browser interactions, and retained diagnostics. Use focused checks while changing code and a separately enforced standard merge profile. The user's current instruction to keep the full run stopped remains in effect.
3. Admit generated tests only after assessing their contribution. They must execute under the standard command, behave repeatably, protect an identified contract, and add useful coverage or fault detection beyond existing scenarios. Counts and line coverage are supplementary signals, not success criteria.
4. Prove selected critical assertions can detect wrong behavior. For a regression use the pre-fix behavior; where appropriate, use a small isolated mutation that bypasses the relevant protection. Run the actual altered application, not a mocked implementation. Keep mutations out of product commits. Apply this selectively rather than making every iteration run an expensive mutation campaign.
5. Review changes to the expected result separately from attempts to make the implementation pass. Test deletion, weakened assertions, new normalizers, baseline updates, new exclusions, and changes to CI/discovery need explicit justification. A second agent can review but cannot establish an independent truth merely by agreeing with the first.
6. Enforce structural rules in code/CI. Test inventory/discovery reconciliation, failing imports, required-profile accounting, and evidence/report completion are mechanical checks. Intent, realistic inputs, meaningful outputs, and legitimate fault-injection boundaries still require review.
7. Track validation quality over time: escaped regressions, flaky or quarantined required checks, failures after harmless refactors, missing assertions exposed by targeted faults, execution cost, and contracts covered. Periodic cleanup should remove demonstrably redundant/brittle checks while preserving unique protection.
8. Keep a clear separation between agent-process compliance and product correctness. We can audit whether an agent used the approved command, changed test policy, or declared completion without evidence; those checks do not substitute for validating files/state/access outcomes.

The reviewed sources do not show a universal industry rejection of mocks or unit tests; Meta's systems explicitly generate unit tests.
