# Validation Coverage Audit and Test Cleanup Plan

## Status and scope

Investigation checkpoint on `dev/test-cleanup`, created directly from `main` at `086b219`. The favorites implementation remains on `dev/UI-favorites` and is excluded from this audit. No product code, tests, workflow files, or protected documentation have been changed. No tests or scenarios have been executed for this investigation; the full validation run remains stopped at the user's request.

The primary comparison is v0.8.0 (`80269ed`) to current main (`086b219`). Coverage introduced in v0.8.0 is listed separately when it exposes an existing gap that persists today. The user's `core/integration` refers to the repository's actual profile, `integration/core`, under `validation/scenarios/integration/core/`.

The questions are whether newer subsystems have scenario coverage and whether the newer scenarios still use the project harness rather than pytest. This is a source and Git-history audit, not a code-coverage measurement or a passing validation result. Finding a scenario proves that explicit checks exist, not that every invariant is tested or that the checks pass on the current branch.

## Executive findings

- Major backend additions since v0.8.0 have substantial scenario coverage: supervised jobs/delegates, Compaction v2/session maps, canonical forks, transcript retrieval, lexical discovery, Explorer import/move/search APIs, model aliases/catalog management, typed settings, SQLite settings import, and default/reset behavior.
- Coverage is incomplete at important boundaries. Actual browser interactions are outside the standard scenario gate. Deployment ingress authentication is tested only by root pytest files; the harness's shared application explicitly disables that authentication policy. Several newer settings migration/reset race checks also exist only in root pytest tests.
- Core scenarios have not switched to pytest. All 139 current core scenario modules contain a direct `BaseScenario` subclass with a `test_scenario` entry point. None imports pytest, uses `unittest.TestCase`, imports root test modules, or launches pytest/Node/browser tests. Python `assert` statements and `unittest.mock` usage are not pytest execution.
- There is assertion-style drift within the harness: some scenarios directly test helper algorithms, and at least two assert on editorial prompt or JavaScript source text. These remain harness scenarios, but harness membership alone does not guarantee compliance with artifact-based validation guidance.
- CI runs `integration/core` and the npm audit policy's direct Node test. The 45 root Python test files and three other direct Node test files on main are not invoked by that workflow. The root suite is supplementary but has acquired sole responsibility for some required contracts.

## Confirmed cleanup findings

### High priority: required tests outside the standard gate

1. Deployment ingress authentication is deliberately bypassed by `validation/core/system_controller.py:99`, which creates the API application with `ASSISTANTMD_AUTH_MODE="disabled"`. No core scenario imports `core.authentication` or asserts owner-login, cookie/CSRF, trusted-proxy ingress, or owner-token throttle behavior. The root authentication files contain these checks; `test_authentication_application.py:62`, `:121`, and `test_authentication_middleware.py:136` provide concrete examples. Add harness scenarios that construct the real application under explicit authentication policies; keep these distinct from resource-principal authorization.
2. Backup-fenced settings reset has an important root-only race check: `validation/test_settings_lifecycle.py:222` changes settings after taking the backup and proves the reset refuses to overwrite the newer edit. The root service test at line 277 verifies the API-service boundary and preservation of state on that conflict. Current `settings_lifecycle` tests a successful reset and a custom-name conflict, not this concurrency contract. Port the race and API error contract into the harness before considering the root tests redundant.
3. The new browser workflows are outside the scenario gate. Core scenarios do not use Playwright, Selenium, Puppeteer, or a Node frontend execution harness. Endpoint/file assertions are valuable but cannot prove actual browser capture, draft retention, control wiring, focus, or asynchronous rendering. Decide how the existing harness should own browser-driven scenarios and evidence; simply adding pytest to CI would execute the separate suite but would not answer the user's concern about maintaining one validation model.

### Medium priority: scenario contract and assertion drift

4. `session_map_schema.py:127` asserts editorial fragments inside authoring instructions, including `durable throughline`. The current guide explicitly rejects substring assertions on editable prompt prose. Keep the structured protocol/version, evidence inclusion, source-range, and provenance assertions; replace prose checks with observable composition or decision behavior.
5. `gmail_connection_api.py:132` reads `static/js/configuration/connections.js` and checks specific JavaScript fragments and UI copy. It executes through BaseScenario but does not execute that client behavior. Replace the source inspection with an actual UI/API behavior check; retain the existing persisted capability/OAuth readiness assertions.
6. `session_map_schema` and `stepped_eviction_planner` are direct model/helper contracts without a bootstrapped runtime. `session_summary_data_retirement` and `transcript_retrieval_storage` also skip `start_system`, but exercise real isolated database artifacts. These four new scenarios are not pytest and should not automatically be discarded as unit tests. Assess whether each helper invariant belongs in a higher-level scenario or is a justified deterministic contract fixture. Preserve the higher-level authoring/post-turn/tool scenarios already covering their integration paths.
7. `validation/core/runner.py:2` has stale pytest wording. Correct it with the eventual harness cleanup so agents do not infer a nonexistent pytest bridge.

### Process and organization

8. Root test placement and multiple runners obscure ownership. There are 40 newly added root test files since the baseline (including direct Node files), alongside the 30 added harness scenarios. Do not delete these root tests wholesale: several duplicate existing scenario contracts, several protect uncaptured failure paths, and several prove browser-only behavior.
9. The guide requires a root-level implementation plan while `.github/workflows/validation.yml:73` rejects non-allowlisted root Markdown at merge time. Keep this investigation plan during branch work as instructed; resolve its approved final destination or removal during merge preparation. No protected documentation may be moved or edited without explicit draft approval.
10. The guide permits focused smoke checks but does not specify the lifecycle of permanent supplementary test suites or require new test files to be part of the standard gate. Any policy correction is deferred until the user is ready to discuss documentation. The existing explicit requirement that deterministic merge contracts belong to `integration/core` still applies.

## Proposed implementation sequence after investigation review

1. Agree on the audit classifications and the desired single validation entry point. Keep the immediate scope to validation cleanup; do not mix the favorites branch or quick-prompts implementation into it.
2. Build an assertion-level migration ledger for every root test: map each required invariant to an existing scenario, a missing scenario assertion, a browser scenario, or an explicitly disposable local smoke check. Prioritize ingress authentication, settings backup/reset races, numbered settings migration failure/retry, then MCP/advanced-shell and ingestion compensation permutations. Record exact scenario destinations before removing anything.
3. Add missing deterministic scenarios/assertions before moving or deleting root tests. Use actual API/files/database artifacts plus existing decision-boundary events. Use controlled provider transports where isolation requires them; avoid broad replacement of the subsystem being validated. Runtime settings and secrets fixtures must use explicit temporary roots, never repository runtime state.
4. Add browser execution as an owned harness capability if browser behavior is to remain a required contract. Scenarios should launch controlled Chromium, load the actual frontend modules or application, record useful failure evidence, and run through `BaseScenario.test_scenario` and normal reports. Decide fixture ownership and CI dependencies before moving existing browser assertions.
5. Remove proven duplicate root tests and migrate necessary remaining checks in focused commits. Replace source-copy/prompt-prose assertions with behavior checks and clarify the stale runner description. Do not conflate bare Python `assert` or controlled transport mocks with pytest usage.
6. Add a structural validation guard that rejects silently undiscovered permanent tests and verifies intended scenario entry points. Verify the standard CI command includes every required deterministic contract through the harness. Keep experimental/live-service probes opt-in.
7. Validate each cleanup slice with fast structural checks and selected scenarios only. The full suite remains stopped; do not run it unless the user explicitly authorizes it later. A source audit is not sufficient to claim the scenarios pass.
8. Review the final diff, run relevant quality gates for any production Python changes, and commit each validated logical unit. Never hide an unresolved contract by deleting its only test or relabeling it as experimental.
9. Documentation review remains deferred: when the user is ready, identify the affected agent guides and architecture/validation documentation, present the exact proposed text or diff, obtain explicit approval, and apply only approved updates.
