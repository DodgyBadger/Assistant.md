## Desired outcome

A user asks for web work in an ordinary AssistantMD chat. The agent can inspect and interact with a website, ask the user to complete a browser step, and continue in the same authenticated context after explicit handback. The user stays inside AssistantMD and briefly opens a lightweight viewer to enter a credential, approve an authentication prompt or complete human verification, then returns control. Closing and reopening preserves the page. Desktop and phone users share the same control and cancellation contract. Human interaction is an interruption to agent work, not an extended browsing session.

Use `web_extract` when retrieval is sufficient, the ordinary read-oriented `browser` for rendered extraction, and interactive browsing when interaction or authenticated access is needed. Search discovers URLs alongside these capabilities. Tasks that clearly require interaction can select it directly. Human assistance in the first implementation is for credentials, authentication and human-verification challenges; it is not a promise to defeat website protections.

Success is an application journey: the agent reaches a human-only step on a controlled external website, the human completes it through the embedded viewer, and the same authorized turn continues using the resulting authenticated page. Optimize the number of steps and the time needed to open, act and return control. Browser startup or a successful screenshot alone is insufficient.

## Human handoff UX goal

The handoff should feel intuitive and seamless within the ongoing chat. When blocked on a human-only step, show a short explanation and an Open browser link beside the waiting agent response. One activation opens the embedded popup on the current page, ready for input, without a separate connection, login or takeover step. The user completes the credential or verification step and presses Return control. After server acceptance, the popup closes and the same agent turn continues automatically; no follow-up chat message, page refresh or manual retry is needed.

Keep the waiting state and next action clear throughout. Closing the popup alone preserves human control, and the same chat link reopens it. A rejected handback stays visible with a useful explanation and preserves the user's page. Connection progress and failures must be understandable without exposing browser-service mechanics. Preserve keyboard focus when opening and closing. Treat the chat-link → ready popup → human step → handback → automatic continuation journey as an explicit UX acceptance goal, including on a phone, rather than merely checking that the individual controls exist.

Useful lessons to preserve:

- Human input and agent observations need separate paths, with exclusive ownership acknowledged by the server.
- Closing a viewer is separate from returning control or closing the remote context.
- Frame capture must not block state observation or control behind font/render readiness; bound operations and separate preview work.
- A viewer must still open after a recoverable navigation/read deadline; extraction is not a prerequisite for help.
- Browser instance identity and observation revisions solve different problems. Delayed responses from an old instance must be rejected even when a replacement starts at a lower revision.
- Bound element selection inside the page before exporting descriptions or handles; many browser round trips can exhaust the deadline.
- Explicit application asset/API paths matter under forwarding. Keyboard input must not disappear during control feedback.

Concrete reasons to replace the prototype foundations:

## Scope and boundaries

Initial scope includes one managed interactive browser process with isolated ephemeral contexts per authorized chat, navigation, bounded page reading, click/fill/select/scroll, brief human takeover, explicit handback, context reuse, desktop/mobile credential entry and verification, cleanup and deployment support. Navigation and general page interaction are agent capabilities; the human viewer only needs enough input to finish the blocking step. Start with the Chromium already packaged by this repository. Select the simplest supported launch/preview transport that passes the actual journey; the prototype's separate CDP process, automation flags and disabled sandbox are not requirements.

Keep browsing in the AssistantMD container and behind the existing application origin/authentication. No browser sidecar, new public port, permanent sidebar, separate browser login, persistent authenticated profiles or credential vault. Profiles belong in owned ephemeral storage, outside configured data/system roots. Human form review/submission workflows, the dedicated Revise instructions flow, a human address bar, browser history controls, tabs/bookmarks, custom desktop-layout switching, custom zoom/pan tooling, upload/download workflows, general tab management, arbitrary agent JavaScript/cookie/network APIs, device-native passkey forwarding, multiple engines and non-web-chat interactive clients are excluded. Unsupported execution contexts, including delegates/workflows initially, receive an actionable result rather than implicitly acquiring another chat's browser.

Preserve ordinary extraction behavior and its existing budgets. Explicit interactive selection reuses a retained context; omitting a URL reads its current page. A subsequent ordinary extraction request must not silently become form-capable merely because a retained context exists. A human-help request explicitly targets interactive operation. Existing user authorization governs website actions; do not invent a blanket approval step for every form action. A user-reserved submission remains reserved after handback.

## Proposed architecture and contracts

### Runtime service and admission

Create a small browser service under `core/`, composed in `core/runtime/bootstrap.py`, held by `RuntimeContext`, and stopped through runtime shutdown after task cancellation is coordinated. Tool and API adapters depend on its typed application operations; core service code does not raise FastAPI exceptions or render HTML. Keep engine-specific handles and frame capture internal.

Use a single admission policy for transient extraction and retained interactive contexts. Retained contexts hold capacity for their lifetime; calls also obey task-call limits and memory-headroom checks. Admission has a bounded result, not an unlimited wait. Never evict active or human-controlled work to admit another task. Centralize current browser budget behavior without broad extraction rewrites. Default capacity must respect existing settings. Use one browser inactivity timeout: 10 minutes by default, configurable through application settings. Start the inactivity clock when handing off to the human; the same waiting turn remains available for handback until inactivity expiry. Accepted human interaction and agent browser activity refresh the clock; an in-flight bounded browser operation is not idle. Passive frame/state polling, an open viewer and the waiting tool itself do not refresh it. There is no separate human-handoff timeout or fixed total browser-session lifetime. Coordinate existing task/tool deadlines so they do not silently impose a shorter human wait; explicit Stop, runtime shutdown and real failures still interrupt it.

Explicit close, owning chat deletion, idle expiry, browser crash and shutdown release contexts, handles, temporary profiles and owned display/browser children. Inactivity expiry closes the context, releases the waiting tool with a clear expired result and renders the handoff link expired; the agent reports that continuation requires a fresh browser session. It does not submit or replay website actions. An explicit Stop before expiry preserves the page under human ownership until explicit continuation or the remaining inactivity period expires; Stop does not start a second retention window. Startup touches no unrelated host browsers. Validate shutdown, forced-parent-exit cleanup, and recovery from a failed launch; do not retain a half-initialized service.

### Identity, observations and ownership

Separate browser instance ID, owning principal/chat, current task lease, handoff generation and page/viewport observation version. These are typed application values with bounded serializable projections. Model-facing element references include or encode the browser and observation version; never substitute the latest server revision for a missing client observation. Reject stale references before dispatch. Invalidate them on navigation, action, takeover, viewport change and instance replacement; also verify the referenced element still belongs to the observed page before acting.

Ownership transitions are serialized with bounded in-flight operations. Requesting human help establishes the waiting task/generation and suspends agent operations before advertising a usable viewer. Opening/reopening claims or confirms human control without creating a second wait. Only an accepted handback for the live owning task/generation wakes that turn. Duplicate requests are safe; delayed input, frame responses, handbacks and continuations cannot act on a replacement instance or superseded turn. Observer disconnect and modal close do not alter ownership.

Model the reachable states explicitly: agent-owned, waiting for human, human-owned, returned, stopped, expired and closed. Document which are durable event statuses versus live service states. A read/navigation deadline can request help with a factual reason; policy denial, missing runtime, capacity refusal and process death remain distinct failures. An action timeout reports uncertain completion, invalidates the observation and requires inspection before another write. No automatic action replay.

### Human input and website policy

Use existing request authority, owning chat/session access, task access and owner-session CSRF rules for all viewer/state/frame/control/input operations. An opaque browser ID alone grants nothing. Keep links same-origin and free of bearer credentials. Restrict capture/caching for private frames and input. Raw CDP is not a public or agent tool surface.

Human input must never become a chat message, model tool argument/result or provider request. Recognized password/OTP controls are unavailable to agent actions/observations, and populated recognized credential fields prevent handback until submitted or cleared. Authenticated page content is intentionally readable after handback. Inspect FastAPI/Pydantic validation failures, request middleware, exception formatting and Logfire capture as well as explicit logging; malformed input must not echo a synthetic credential sentinel into logs or artifacts. Never retain live frames, keystrokes, cookie values or browser profiles as evidence.

Use the shared `core/web/security.py` policy for targets and browser request checks, with deliberate redirect/subrequest coverage. Interactive operations allow requests needed for authorized forms; extraction remains read-oriented. Treat WebSockets, service workers and popup/new-window navigation explicitly rather than assuming an HTTP route callback covers them. Keep unsupported surfaces blocked with actionable behavior. Support same-tab sign-in and one authentication popup/new page at a time within the owning browser context. The server-side popup is a separate page in that context; the existing modal temporarily shows its rendered pixels and routes human input to it. Do not open another client modal/window or add a tab strip. Show a small sign-in-window indicator and a way to return to the original page while the popup remains open. On popup closure, restore the original page automatically. Bind frames, input and observations to page identity as well as browser/viewport version so delayed responses cannot target the wrong page. Apply the same authority, credential, network and resource policy to both pages. Reject additional popups with clear feedback. Authentication completion without popup closure must leave an obvious path back; do not infer successful authentication solely from a window closing.

DNS validation alone is not socket-pinned egress isolation. Record the current guard's limits and test the policies actually enforced; do not claim comprehensive SSRF protection from preflight resolution. Likewise, filtering known credential controls does not prevent a hostile site reflecting a secret into visible content. Arbitrary trusted code with application/OS authority is outside this cooperative input boundary. Inspect advanced-shell/helper access to protected input/CDP endpoints before making stronger claims. Keep actual page URLs intact internally and distinguish safe display/log URLs from navigable URLs.

### Chat events and minimal human viewer

Use canonical task-owned execution and cancellation. Add a typed handoff projection with browser reference, task/generation, safe reason and status to live events, compact replay and minimal durable history. Enumerate exact history/schema changes before coding; reuse current chat storage mechanisms without persisting cookies or live browser state. After process restart, old history renders an expired session. Terminal events must not leave a stale actionable waiting prompt. Extend existing event-buffer/replay scenarios where those contracts belong.

Implement the viewer as a normal frontend module using existing modal/focus conventions, not inline styles in the stream parser. Return control closes the viewer only after server acceptance. Modal close unloads preview work; reopening preserves page/control. State, input/control and preview remain independently responsive. The initial surface contains the rendered page, a short reason/site indicator, Close and Return control, plus actionable connection/error feedback. While an authentication popup is displayed, include only its sign-in-window indicator and a return-to-original-page action; this does not introduce general tab management. Pointer/touch activation, typing/paste/deletion/composition, basic keys and scrolling must work for credential and verification steps. Do not add navigation chrome or a browser toolbar. Use bounded capture/polling only while visible, and stop frame production/request work when the viewer closes; the agent can continue without a live preview. Preserve supported forwarding/base-path behavior with explicit URL construction and an external proxy fixture.

Chat Stop uses the existing task cancellation path, invalidates the waiting task's handback authority and preserves the page under human ownership until expiry or an explicit server-validated continuation by a later authorized turn. Ordinary chat remains the place to change instructions. The dedicated viewer-to-composer revision flow and its extra orchestration are deferred. Stale handback must never resume a cancelled or superseded task. Stop cannot undo an already completed external-site action.

Adapt the page viewport and coordinate mapping to the usable viewer area on desktop and phone without recreating the context or losing authentication. Publish viewport/version with frames and reject stale input after resizing. Keep the phone surface compact, respect keyboard/safe areas, and support touch scrolling and a local input bridge for typing, paste, deletion and composition. Desktop keydown forwarding alone is insufficient. Device-profile emulation, layout overrides and custom zoom/pan are not initial requirements; add complexity only if an actual credential/verification acceptance case demonstrates the need. Verify native keyboard and touch on a real phone beyond viewport emulation.

### Settings, packaging and observations

Use existing settings installation/repair conventions for the single browser inactivity setting. No new environment-only feature switch or secrets/profile migration. Explicitly list settings and minimal chat history schema additions in the first implementation slice. Configured data/system roots are persistent runtime state; all automated acceptance uses isolated roots.

The existing Dockerfile supplies Playwright's matching full Chromium; verify display helpers, libraries, fonts, TLS trust, permissions, writable temporary storage and process reaping in the final non-root image. Runtime startup must not download/install packages or use investigation files under `/tmp`. Development preflight distinguishes missing browser, display/library and permission failures. Chromium’s own sandbox is required in both development validation and production, for extraction and retained interactive browsing. Set sandbox intent explicitly, fail with actionable diagnostics when unavailable and never silently retry unsandboxed. Container isolation does not replace the browser sandbox. Validate both the supported production capability set and the fully dropped-capabilities development configuration: an ordinary application-user chroot must remain denied, while Chromium’s nested-user-namespace chroot must work. The supported production image and actual launch policy must pass sandboxed headless and headed acceptance before release; a development-only success cannot satisfy that gate.

Use one tracked `docker/browser-seccomp.json` for development and production. The production `assistant` Compose service references it with `seccomp=./docker/browser-seccomp.json`; development launchers copy/reference the same bytes on their launch host. Retain the pinned upstream revision, digest, modification description and licence alongside it. A custom profile replaces the complete Docker default: review the baseline on runtime updates and validate each supported host rather than maintaining divergent dev/production policies. The shared profile passes the development runtime preflight; that does not establish application launch wiring or production compatibility. S3 stays open until application and supported production-image acceptance pass.

Production upgrades that introduce the policy require the updated Compose file and tracked JSON on the launch host as well as the new image, followed by container recreation. With the current repository-based installation, `git pull`, `docker compose pull` and `docker compose up -d` deliver those pieces. An image-only pull or restart cannot introduce a new creation-time policy. Installation-guide updates for this requirement must be drafted and approved during the final documentation review; redesigning the basic installation process remains out of scope.

No Docker/Podman/containerd daemon socket, engine-control API, privileged mode or broad capability addition is permitted for the application or agent containers. Container creation/security-profile changes are deployment operations performed outside the application container; browsing must never require runtime access to the container engine. Preserve non-root execution, no-new-privileges and the surrounding capability/network/resource restrictions.

If the production host/container denies Chromium’s required namespace operations, address that as a production deployment prerequisite with a narrowly reviewed runtime policy. A seccomp change affects the whole application container, including an LLM-accessible CLI, not only Chromium children. Compare the complete proposed policy against the actual runtime baseline and assess any AppArmor/host restrictions independently; the upstream Playwright profile prepared for development is a candidate for investigation, not an approved production replacement. Record and peer-review the security tradeoff, then validate the exact policy in the supported deployment. If the required browser and outer-container protections cannot coexist, browsing remains unavailable and the feature is not release-ready; do not resolve the conflict through an unsandboxed or more privileged fallback.

Validate within the current AssistantMD service's 2 GiB/one-CPU limit and shared-memory/security configuration. Existing deployment services remain as configured; browsing adds none. Measure app baseline, cold/warm browser launch, active site, short human viewing, retained contexts, expiry and cleanup. Measure viewer open-to-usable time, frame latency, transferred bytes and hidden-viewer capture work. Choose adequate bounded frame resolution/quality/cadence for readable credentials and challenges, rather than smooth continuous desktop streaming. A lighter on-screen viewer does not imply a smaller browser engine: Chromium must remain alive after handback to preserve authenticated state while the agent works. Do not promise engine memory savings from short human visits; optimize demand-driven preview and cleanup first. Report browser process memory separately from container usage and interval measurements separately from lifetime peaks. Capacity refusal must preserve chat/API availability. Emit sanitized lifecycle/admission/ownership/deadline/cleanup observations correlated to session/task/browser identity, without per-key or per-frame logging.
