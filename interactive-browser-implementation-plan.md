# Interactive browser implementation plan

Status: draft for review, 2026-11-06. This plans a replacement for the disposable experiment; it does not authorize implementation or protected documentation edits. Runtime location is agreed: inside the Assistant.md container. Chromium is the recommended initial engine, with the lighter-engine question and evidence captured below.

## Outcome and scope

A user asks for web work in an ordinary chat. The agent uses `web_extract` first when page retrieval is sufficient, escalates to the default non-interactive `browser` when rendering is needed, and selects an interactive browser when interaction, authenticated access or a browser-specific block requires it. Search discovers candidate URLs alongside this progression. Tasks that explicitly require forms or sign-in can go directly to interactive mode.

When human help is needed, the current chat shows a compact Open browser action. It opens a large embedded viewer within Assistant.md. The user completes sign-in, MFA or a CAPTCHA, returns control, and the same agent turn resumes against that browser context. Closing the viewer alone leaves control with the human; reopening the action restores the viewer. There is no permanent browser sidebar, separate browser login, new public port or browser sidecar.

Include navigation, bounded page/element reading, clicks, text entry, selections, scrolling, human takeover and context reuse across chat turns. Existing user authorization governs actions; authenticated access does not expand the task's scope. Upload/download workflows, persistent browser profiles, device-native passkeys/security-key forwarding, multiple browser engines, Telegram, cross-session messaging, arbitrary browser JavaScript tools and a general browser-management dashboard are outside this implementation.

## Evidence to preserve before discarding the prototype

- Live DigiKey browsing succeeded after human challenge completion, including handback, search and catalogue filtering. Amazon search succeeded after correcting query/control selection. The grants portal exposed authenticated dashboard and application navigation. These establish feasibility on those sessions, not universal site compatibility or a newly performed login on every site.
- The most recent live session is `Personal_20261106_135915_32_a2rx`. Keep a sanitized summary of observations; do not copy private portal contents, account identifiers or authenticated URLs into product documentation.
- A preview operation waiting on fonts blocked controls. State, control and preview must remain independently responsive; capture the current rendered frame rather than waiting for publication-style screenshot readiness.
- Per-element browser round trips on large pages exhausted operation deadlines. Select and describe a bounded element set in the page before exporting handles. Retain actual element references and reject stale revisions.
- Extraction/navigation deadlines suppressed the human-help link. Explicit human help must not require successful extraction; a recoverable read/navigation timeout must offer takeover. An empty extraction alone is not evidence of a CAPTCHA.
- Codeman forwarding lost relative viewer asset/API paths. Use explicit same-origin routing and validate nested deployment paths/base-URL interference, including CSRF and existing application authentication.
- Browser identity must change on reset/restart; reject late responses from retired contexts without rejecting a new context's lower revision. Browser state is lost on application restart, and the UI must explain expired sessions.
- A forced development restart left an orphaned Chromium/display pair. Normal shutdown callbacks alone are insufficient lifecycle evidence.
- One resource snapshot attributed approximately 606 MiB PSS to the active browser/display and 264 MiB to an orphan. The development cgroup had no memory limit and included unrelated work and filesystem cache. These figures do not establish that the supported 2 GiB deployment is sufficient; remeasure under the real Compose limits.

The root `browser-handoff-experiment-plan.md` and ignored `validation/runs/browser-handoff/` artifacts contain the investigation history and smoke evidence. Capture the useful baseline before removing experiment imports, special flags, `/tmp` dependency discovery and prototype routes from the production path. Do not promote the experiment wholesale or treat its smoke scripts as production acceptance scenarios.

## Browser choice

Start with Chromium because this repository already packages it and the successful prototype depends on its launch/CDP/frame-capture path. This is an evidence-based initial choice, not a claim that Chromium is the smallest engine or cannot be replaced.

Short human interaction reduces viewer/streaming cost, but the browser must remain alive afterward to preserve authentication while the agent works. JavaScript, navigation, challenge and authentication compatibility remain necessary even when visual fidelity is unimportant. Playwright supports Chromium, Firefox and WebKit; its documented `connect_over_cdp` path is Chromium-specific. Embedded WPE WebKit explicitly targets a small footprint, but it is not a drop-in replacement for the tested transport/viewer and has no measured memory or compatibility result here.

Do not implement a browser-engine abstraction or ship multiple engines in the first version. Keep the application service interface independent of Playwright/CDP so a later bounded engine comparison can reuse the same application behavior. A future comparison must measure cold/warm startup, idle and active PSS, container memory, and successful sign-in/challenge/form workflows on representative sites before promising savings or parity. First pursue launch-on-demand, context limits, reliable cleanup, idle expiry and preview suspension.

Sources: [Playwright browsers](https://playwright.dev/python/docs/browsers), [Playwright CDP connection](https://playwright.dev/python/docs/api/class-browsertype#browser-type-connect-over-cdp), [WPE WebKit design goals](https://webkit.org/wpe/).

## Architecture and contracts

### Managed in-container service

Create a browser service under `core/`, owned by `RuntimeContext` and wired through bootstrap/shutdown. Follow ADR 0001; remove the prototype's process-global service construction and API-to-core experiment dependencies. The service lazily owns the headed Chromium process, the optional Linux virtual display, browser contexts, operation deadlines and cleanup. Headless extraction retains its lightweight call contract and participates in the same resource admission policy.

Use one managed interactive browser process with isolated contexts keyed by execution principal and chat-session identity. Chat/vault/session access checks remain authoritative. Never resolve browser access solely from an unguessable browser ID. New contexts start unauthenticated; reuse is restricted to the owning chat. Delegates and workflows cannot acquire a chat's browser implicitly; initially reject interactive calls outside supported chat execution contexts with an actionable result.

Count retained contexts against capacity, not just the duration of individual tool calls. Honor the existing browser concurrency, memory-headroom and task-call budgets; define how these settings govern short-lived versus retained sessions without creating an unbounded second lane. Admission must either make progress or return a bounded capacity result. Do not evict an actively used or human-controlled context to satisfy another request.

Retain browser contexts across turns while within the idle lifetime. Proposed starting defaults are a 15-minute idle expiry and a 10-minute human-help wait, subject to deployment measurements; human waits have their own deadline and must not be accidentally classified as idle. Explicit close, owning chat deletion, expiry, crash and shutdown release contexts and owned processes. Do not place profiles in `data/` or `system/`; use owned ephemeral storage. Startup must not kill unrelated host browsers. Ensure child process reaping and parent-death behavior work in the supported container and development environments.

### Tool and escalation policy

Keep the existing `browser` tool name and non-interactive default. Add a documented `interactive` selector, typed element actions and an explicit human-help request with a short reason. Reuse an existing interactive context for subsequent calls in the same chat; omitting `url` means inspect or act on its current page. Continue to keep URLs and element revisions distinct from context identity.

Separate navigation, observation, interaction and human-help operations internally. A requested human-help operation publishes its link once a usable browser exists, regardless of extraction success. Recoverable navigation/read deadlines offer takeover with a factual explanation; invalid targets, missing dependencies, exhausted capacity and dead browser processes produce distinct actionable failures. Do not treat all errors as human challenges. Failed writes are never automatically replayed; inspect the resulting state before repeating a possibly completed action.

While human control is acknowledged, reject agent browser operations. Serialize ownership changes with in-flight operations, bound those operations, invalidate element references on takeover/navigation/action and publish coherent completed state. The agent resumes only after explicit successful handback. Chat Stop cancels the waiting tool/turn without silently returning browser control or repeating actions. A later explicit human-help request can reattach to the retained context.

Use one network-policy implementation for public target validation, redirects, subrequests and denied local/private addresses. Preserve default extraction's read-oriented behavior; interactive mode allows the requests necessary for user-authorized forms. Do not expose raw CDP, arbitrary evaluation, network interception, cookie export or token APIs as agent tools. Keep actual navigation URLs intact internally; shape agent-visible URLs without accidentally breaking search parameters or exposing sensitive authentication parameters.

### Embedded viewer and chat continuation

Use protected same-origin API/UI routes under the existing application authentication boundary, principal/session authorization and owner-session CSRF rules. Do not add a public viewer service or put bearer credentials in tool results or links. Direct API calls must enforce the same ownership and authority checks as the viewer.

Represent human help as a typed chat event with browser identity, safe viewer reference, reason and waiting/returned/expired/stopped state. Preserve it through stream reconnection and compact replay; persist the minimal nonsecret reference/status needed for history rendering. After process restart, an old reference displays expired and a new browser can be requested. Do not present an old link as a live authenticated session.

Open the viewer in a large accessible modal with a close action, keyboard/focus behavior and the existing screen/input controls. Return control closes the viewer only after the server accepts handback; a rejected handback remains visible with a useful explanation. Closing the modal unloads preview polling without changing backend ownership. Reopen works while the tool waits. Show navigation progress and actual connection/operation failures rather than a generic error or an indefinite connecting label. Normalize ordinary hostname input to HTTPS while retaining server-side URL policy.

Stream or poll frames only while the viewer is visible. State observation and takeover remain responsive during delayed frame capture. Serve assets and API calls from explicit application/browser paths that remain valid under supported forwarding and base-path deployments. The viewer displays the remote page's rendered pixels; destination websites are not themselves embedded as third-party iframes.

### Credentials and execution boundary

Human input is a separate ingress path: it must not be constructed as a chat message, agent tool argument, tool result or provider request. The model-facing browser contract excludes recognized password/OTP controls and raw cookies/tokens. Refuse handback while recognized credential fields remain populated; allow submit/clear before handback. Authenticated page content, including displayed account identity and application information, is intentionally readable by the agent after handback and may enter chat/provider context.

Audit the complete human-input path, including automatic FastAPI/Pydantic errors, middleware, tracing, request-body capture and exception formatting. Disable or redact credential-bearing capture at those boundaries. Do not retain live screenshots, keystrokes, raw request bodies, profiles or cookies in activity logs, chat events, validation artifacts or traces. A sanitized error must still distinguish rejected ownership, denied URL, deadline, expired context and browser failure.

Check the supported advanced-shell and workflow/helper network surfaces against the browser/CDP/human-input endpoints. Existing deployment authentication and principal authority must remain in effect; do not give agent tools the owner's authentication/CSRF material. Document the actual boundary: this prevents credential delivery through the supported tool/input path, not access by arbitrary trusted code sharing application process/OS authority. A site that reflects secrets into visible content remains a separate risk; do not promise universal credential invisibility based only on filtering recognized input fields. Strong isolation from unrestricted code is not claimed by an in-container design.

### Packaging, settings and observability

Update `docker/Dockerfile` and development setup to include the selected Chromium, runtime libraries and Linux display support at build/setup time. Runtime startup must not install packages or require a root login. Reuse Chromium for both modes; verify whether the separate headless-shell download is unnecessary with the selected launch configuration. Prefer the browser sandbox where supported and make any required exception explicit and validated; do not blindly copy the prototype's disabled-sandbox flags.

Keep the supported Compose topology as one Assistant.md service for browsing. Validate under its current 2 GiB/one-CPU limit, shared-memory ceiling and security options. Measure app-only baseline, first browser launch, representative active site, handoff, multiple retained contexts, expiry and cleanup. If required headroom cannot be maintained, return a clear capacity result and report measured deployment requirements before proposing configuration changes. Memory pressure must not crash chat/API service or cause unlimited queueing.

Use the existing settings system for bounded browser policy and any necessary retention/wait settings; follow settings installation/repair conventions rather than new environment-only app behavior. Deployment authentication remains infrastructure configuration. No authenticated browser persistence, secrets-store migration or browser-profile database is introduced. Explicitly enumerate any minimal chat-event/history schema changes before implementation.

Emit sanitized lifecycle, admission, ownership, deadline, handoff, expiry and cleanup observations correlated to principal/session/task/browser identity. Include bounded resource measurements at meaningful milestones, not per-keystroke or per-frame logs. Distinguish browser-process memory from container memory/cache, and interval measurements from lifetime peaks.

## Agent instruction changes

Keep always-present instructions short and put the detailed contract in the existing virtual tool documentation, following ADR 0008. The default progression is `web_extract` → non-interactive `browser` → interactive `browser` → human takeover; search is a discovery tool alongside it. Allow direct interactive selection when forms or authenticated access are clearly required. Escalate on observed limitations and avoid repeated identical failing calls.

Tell the agent how to request human help, wait and resume the same task; explain context reuse, current-page reads, element revisions, bounded results and action-timeout uncertainty. Never ask for passwords, MFA codes, cookies or tokens in chat/tool arguments. Explain that authenticated page content is available while human-entered credentials follow the separate input path. Do not infer a CAPTCHA from an empty result or claim a site is unreachable when only extraction failed. Any action approval requirements come from the existing task/authorization contract, not a blanket new confirmation rule for every form field or save.

## Implementation slices and acceptance evidence

Use the installed behavioral planning/writing/review skills for the durable implementation. Before each new slice, write the smallest meaningful acceptance condition through real production entry points and capture a genuine missing-behavior red result, then preserve that condition through the green run. For behavior already present in the prototype, retain an honest green characterization baseline; demonstrate required production differences, not artificially wrong expectations or setup failures. Do not edit assertions simply to turn a failure green.

1. **Replace experiment ownership with the runtime service and resource policy.** Start with real bootstrap and a deterministic local synthetic website. Extend `test_browser_call_budget.py` for the shared admission contract and add focused lifecycle coverage for retained contexts, expiry and process release. Observe real denied calls, per-chat isolation, browser/context closure and owned process exit. Verify forced parent exit under an isolated subprocess so orphan prevention is an observed result.
2. **Wire the production browser tool and bounded observations.** Exercise normal extraction unchanged, first interactive call, reuse, navigation and element-based fill/select/click against the controlled site. A large-page case must return bounded actionable results within the deadline; stale elements and agent calls during human ownership must be rejected. A slow response must still produce human help, while invalid URLs and resource failures retain their own semantics. Do not auto-submit or replay a timed-out write.
3. **Complete one application-level handoff journey.** Through real chat HTTP/SSE entry points and the real rendered Assistant.md UI, use a narrow deterministic external model response fixture to select tool calls. Sign in to the synthetic external website through the embedded viewer, close/reopen without handback, return control and verify same-turn authenticated continuation. Include stream reconnect/replay, Stop while waiting, an expired/restarted context and request rejection outside the owning session. Extend `test_chat_task_event_buffer.py` where the event/replay contract belongs rather than duplicating those assertions in every UI case.
4. **Audit the credential path within that same journey.** Use synthetic sentinel password/OTP/cookie values. Register them with the artifact policy before any capture; inspect actual outbound model requests, persisted chat/tool history, application logs, telemetry capture and retained artifacts for absence of those values while authenticated page content remains available. Verify unauthorized/CSRF-invalid human API requests and credential-populated handback refusal. This proves the supported path on the fixture, not universal secret detection or OS-level isolation.
5. **Package and validate the deployment and agent guidance.** Run cold setup/start and the same essential handoff in the built container under supported limits; verify no runtime installation, extra port or sidecar is needed. Validate forwarding/base-path interference and embedded assets with an external proxy fixture. Use a small provider-boundary fixture to verify that the published descriptions/virtual docs expose the escalation and handoff contract; evaluate real model choice and public sites manually as opt-in observations, not deterministic pass gates.

Keep Chromium, application services, task execution, admission, persistence, viewer and control API real. Substitute only external model responses, external websites and forwarding-layer behavior where determinism requires it. Fixtures use isolated temporary data/system roots and a tightly scoped local-site network allowance; do not add a production private-network bypass. No real accounts, purchases or submissions are required for deterministic checks. Retain correlated observations, scenario source/digests and red/green reports under `validation/runs/` according to the existing harness policy; do not retain raw authenticated page snapshots or credentials.

Run fast relevant scenarios while developing, plus `uv run ruff check .`, `uv run black --check .`, `uv run mypy api core`, and relevant JavaScript/build checks before delivery. During hardening/merge preparation run `uv run python -m pytest validation/scenarios/integration/core`. Browser/deployment/live-service profiles are explicitly opt-in and must be run for this feature's acceptance; report any unavailable environment as an unresolved validation limit rather than silently treating skipped checks as success.
